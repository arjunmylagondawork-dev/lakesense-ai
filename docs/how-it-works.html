LakeSense AI · How it works

A data pipeline that checks its own data and explains what went wrong.

Messy source files go in, every day. Only the new ones are loaded; corrections are merged, customer changes are kept as history, and broken files are turned away at the door. Clean Delta Lake tables come out, along with AI reports on rejected records and schema changes, alerts on unusual revenue days, and a way to ask the data questions in plain English, with safety checks on every query.

    The AI layer
    
  
    The AI is used where it helps a data team, and kept away from what it is bad at. Statistics find the problems; the language model explains them. Anything the model writes is treated as untrusted input.
    
  
    
    
    
      
    1 · Data-quality incident report
    
      
    "Why were 1,861 rows rejected last night?"
    
      
      
        
    1. Silver counts failures for every rule in a single pass and saves sample bad values.
      2. 
        
    2. A health score is computed: per table, failure rates are weighted (errors count more than warnings).
      3. 
        
    3. The LLM writes a Markdown report: summary, findings table, likely root cause, impact, and a fix snippet for each failing rule.
      4. 
      
    
    
    
    
    
      
    2 · Revenue anomaly alerts
    
      
    "Revenue looks strange on Tuesday."
    
      
      
        
    1. Divide each day by a weekday index, so a normal busy Saturday isn't flagged.
      2. 
        
    2. Score each day against the previous 14 days with a robust z-score (median and MAD, so one outlier can't skew the baseline).
      3. 
        
    3. For each flagged day, compare category revenue with its baseline. The LLM explains the likely cause and what to check next.
      4. 
      
    
    
    
    
    
      
    3 · Ask your data (text-to-SQL)
    
      
    "Top 10 customers by spend?"
    
      
      
        
    1. The LLM gets the warehouse schema and writes one SQL query.
      2. 
        
    2. Guardrails check it (see the playground below). Unsafe SQL is blocked and never retried. If the tables can't answer the question, it says so instead of guessing.
      3. 
        
    3. The query runs on a read-only connection that can't touch files. If the SQL is malformed or errors, the message goes back to the LLM to fix (up to 2 retries). Every attempt is logged.
      4.

    Design choices
    
  
    
    
    
      
    ChoiceWhy
    
      
    Bronze stores text onlyIf casting happens at ingest, a bad value silently becomes NULL and the original is lost. Keeping text means silver can be fixed and replayed from bronze.
    
      
    try_cast / try_to_timestampSpark 4 turns on ANSI mode, where one bad value fails the whole job. Safe parsing lets the quality rules catch it instead.
    
      
    Error vs. warn rulesBlocking every imperfection throws away real revenue. Warnings are reported and scored, but the row continues.
    
      
    Dimensions before factsOrders are checked against clean products and customers, so cascading failures become visible in the report.
    
      
    Statistics detect, LLM explainsLLMs can invent alerts and get arithmetic wrong. They only write the explanation, from numbers they are given.
    
      
    Mock LLM by defaultAnyone can clone and run the full flow in minutes, and CI tests it with predictable output. Switching to a real model takes one environment variable.
    
      
    Incremental, idempotent loadsA manifest of loaded files and processed batches means re-runs and Airflow retries never duplicate data, and only new work is done.
    
      
    MERGE with "newer wins"A late correction updates the original row; an old replay can never overwrite newer data.
    
      
    Contracts before ingestionHeaders are checked before Spark reads a file, so one broken file is rejected on its own instead of failing the whole batch.
    
      
    Delta Lake, Parquet fallbackDelta gives ACID MERGE, time travel and OPTIMIZE; the same code runs on plain Parquet, and CI tests both.
    
      
    Atomic warehouse publishThe DuckDB file is built under a temp name and swapped in, so the app never reads a half-built warehouse.

    Run it yourself
    
  
    Needs Python 3.10+ and Java 17+.
    

    git clone https://github.com/arjunmylagondawork-dev/lakesense-ai.git && cd lakesense-ai
python -m venv .venv && source .venv/bin/activate
pip install -e ".[app,dev]"

lakesense all                              # full load → bronze → silver → gold → warehouse → AI reports
lakesense generate --append-days 7         # land a week of new files
lakesense run                              # incremental: only the new files, MERGE + SCD2
lakesense ask "top 5 customers by spend"   # plain English → guarded SQL → answer
streamlit run app/streamlit_app.py         # dashboard on http://localhost:8501
pytest                                     # 53 tests
    
  
    Or run docker compose up --build, then open localhost:8501.
